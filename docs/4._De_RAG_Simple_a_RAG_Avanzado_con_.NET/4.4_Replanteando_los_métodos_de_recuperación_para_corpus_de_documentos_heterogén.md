# 4.4 Replanteando los métodos de recuperación para corpus de documentos heterogéneos

En un entorno empresarial real, es poco común encontrarse con un conjunto de datos perfectamente uniforme. A medida que escalamos de una prueba de concepto a una solución de producción, nos enfrentamos a **corpus de documentos heterogéneos**: colecciones que mezclan manuales técnicos densos, correos electrónicos informales, tablas financieras, contratos legales y transcripciones de llamadas.

Tratar todos estos documentos con una única estrategia de fragmentación (*chunking*) y un único índice vectorial suele degradar la precisión del sistema. En esta sección, analizaremos cómo replantear la recuperación para adaptarla a la diversidad estructural y semántica de los datos.

### El desafío de la heterogeneidad

Cuando aplicamos una técnica estándar (como fragmentos de 500 tokens con un solapamiento del 10%) a documentos heterogéneos, surgen varios problemas:

1.  **Pérdida de contexto estructural:** Un fragmento de un contrato legal necesita referencias a la cláusula superior, mientras que un fragmento de un manual técnico necesita saber a qué producto se refiere.
2.  **Densidad de información variable:** Un párrafo de una normativa técnica puede contener diez veces más "entidades" que un párrafo de una comunicación interna.
3.  **Ruido semántico:** Los términos comunes en un tipo de documento (ej. "cláusula" en legal) pueden actuar como ruido cuando el usuario busca información técnica.

### Estrategias de recuperación adaptativa

Para solventar esto en .NET, debemos movernos hacia una arquitectura de recuperación que reconozca el tipo de contenido antes y durante la consulta.

#### 1. Clasificación de Documentos y Enrutamiento de Ingesta
En lugar de un pipeline lineal, implementamos un flujo de trabajo que clasifica el documento al inicio. Podemos utilizar metadatos o incluso una llamada ligera a un LLM para etiquetar el "tipo de documento".

```csharp
public enum DocumentType { Technical, Legal, General, Financial }

public class DocumentProcessor
{
    public async Task ProcessDocumentAsync(Stream pdfStream, string fileName)
    {
        // 1. Identificar el tipo (puede ser por metadatos, nombre o análisis de contenido)
        DocumentType type = IdentifyDocumentType(fileName);

        // 2. Seleccionar la estrategia de fragmentación basada en el tipo
        var chunks = type switch
        {
            DocumentType.Legal => await LegalChunker.SplitAsync(pdfStream),
            DocumentType.Technical => await TechnicalChunker.SplitAsync(pdfStream),
            _ => await StandardChunker.SplitAsync(pdfStream)
        };

        // 3. Enriquecer con metadatos específicos del dominio
        var enrichedChunks = chunks.Select(c => new VectorRecord 
        {
            Content = c.Text,
            Metadata = new Dictionary<string, object> {
                { "doc_type", type.ToString() },
                { "source", fileName }
            }
        });

        // 4. Upsert a la base de datos vectorial
        await _vectorStore.UploadAsync(enrichedChunks);
    }
}
```

#### 2. Enriquecimiento de Metadatos para el Filtrado Previo (*Pre-filtering*)
En corpus heterogéneos, la similitud vectorial por sí sola suele ser insuficiente. Un "replaneamiento" efectivo implica el uso intensivo de metadatos. Al recuperar, no solo buscamos por "proximidad", sino que restringimos el espacio de búsqueda.

Si el usuario pregunta "¿Cuál es el periodo de garantía del modelo X?", el sistema de recuperación debería ser capaz de filtrar primero por documentos de tipo `Technical` y modelo `X` antes de realizar la búsqueda vectorial.

#### 3. Índices Múltiples vs. Índices Particionados
Dependiendo de la disparidad de los datos, podemos optar por:
*   **Colecciones separadas:** Crear un índice en Qdrant o Azure AI Search para "Contratos" y otro para "Manuales". Esto permite usar diferentes modelos de *embeddings* si fuera necesario (por ejemplo, un modelo especializado en lenguaje legal).
*   **Particionado lógico:** Usar un único índice pero con campos de filtrado optimizados.

### Implementación en C#: Recuperación Selectiva con Semantic Kernel

Podemos utilizar la capacidad de filtrado de los conectores de memoria en .NET para realizar búsquedas en corpus heterogéneos de manera eficiente.

```csharp
using Microsoft.SemanticKernel.Connectors.Memory.AzureAISearch;
using Microsoft.SemanticKernel.Memory;

public async Task<List<MemoryQueryResult>> SearchInHeterogeneousCorpus(string query, DocumentType targetType)
{
    // Configuramos el filtro para limitar la búsqueda al tipo de documento detectado en la intención
    var filter = $"doc_type eq '{targetType}'";

    var searchOptions = new AzureAISearchMemoryRecordSearchOptions
    {
        Filter = filter,
        IncludeEmbeddings = false,
        Top = 5
    };

    // Buscamos solo en la porción relevante del corpus
    var results = _memory.SearchAsync("enterprise-docs", query, limit: 5, minRelevanceScore: 0.7);
    
    // Nota: Dependiendo de la implementación del conector, el filtrado por metadatos 
    // se pasa a través de las opciones específicas del proveedor.
    return await results.ToListAsync();
}
```

### El rol de la "Jerarquía de Recuperación"

Al replantear la recuperación, dejamos de ver el documento como una lista plana de fragmentos. Para documentos heterogéneos complejos, se suele implementar una **recuperación de dos niveles**:

1.  **Nivel de Resumen:** Primero se busca en un índice que solo contiene resúmenes de documentos completos. Esto identifica qué documentos (o secciones de documentos) son relevantes.
2.  **Nivel de Detalle:** Una vez identificado el documento (ej. "Manual_Seguridad_v2.pdf"), se realiza la búsqueda vectorial detallada únicamente dentro de los fragmentos pertenecientes a ese documento.

Este enfoque reduce drásticamente las "alucinaciones de recuperación" donde el sistema mezcla información de dos documentos que parecen similares semánticamente pero pertenecen a contextos corporativos distintos.

### Conclusión técnica
Replanteamiento no significa necesariamente mayor complejidad algorítmica, sino **mayor precisión en la segmentación de los datos**. Un corpus heterogéneo requiere que el pipeline de RAG en .NET deje de ser "agnóstico al formato" y pase a ser "consciente del contexto", utilizando el tipado fuerte de C# y las capacidades de filtrado de las bases de datos vectoriales modernas para compartimentar el conocimiento.
