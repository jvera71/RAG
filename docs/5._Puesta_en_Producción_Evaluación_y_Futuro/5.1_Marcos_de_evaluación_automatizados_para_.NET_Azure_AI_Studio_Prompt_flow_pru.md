# 5.1 Marcos de evaluación automatizados para .NET (*Azure AI Studio Prompt flow, pruebas unitarias de LLM con xUnit/NUnit*)

La evaluación es una de las fases más críticas y, a menudo, más complejas en el ciclo de vida de una aplicación RAG. A diferencia del software tradicional, donde las salidas son deterministas, los LLMs introducen variabilidad. El objetivo de los marcos de evaluación automatizados en .NET es transformar métricas subjetivas ("la respuesta parece buena") en datos cuantitativos y reproducibles.

### 5.1.1 El paradigma de "LLM-as-a-Judge"

En el ecosistema .NET, la evaluación automatizada se apoya frecuentemente en el concepto de **LLM-as-a-Judge**. Esto implica utilizar un modelo de lenguaje con capacidades superiores (como GPT-4o) para calificar las respuestas generadas por nuestro pipeline de RAG (que podría usar un modelo más pequeño o específico).

Las métricas clave que debemos automatizar son:
1.  **Groundedness (Veracidad):** ¿La respuesta se basa únicamente en el contexto recuperado?
2.  **Relevance (Relevancia):** ¿La respuesta aborda directamente la pregunta del usuario?
3.  **Coherence (Coherencia):** ¿La respuesta es fluida y lógica?

---

### 5.1.2 Azure AI Studio: Prompt flow

**Prompt flow** es una herramienta de desarrollo dentro de Azure AI Studio que permite agilizar todo el ciclo de desarrollo de aplicaciones de IA, centrándose especialmente en la evaluación. Aunque gran parte de la orquestación se puede realizar visualmente, su integración con .NET es fundamental para equipos que buscan robustez empresarial.

#### Evaluación por lotes (Bulk Test)
Prompt flow permite ejecutar un "Dataset de prueba" (un archivo JSONL con preguntas y contextos esperados) contra nuestro pipeline de .NET expuesto como un endpoint. 

**Componentes de evaluación en Prompt flow:**
*   **Built-in Evaluators:** Azure proporciona evaluadores preconfigurados para RAG que calculan puntuaciones de 1 a 5 basándose en razonamiento matemático.
*   **Custom Evaluators:** Podemos escribir lógica personalizada en Python o C# para validar reglas de negocio específicas (por ejemplo, que la respuesta no mencione a la competencia o que cumpla con un formato JSON estricto).

### 5.1.3 Pruebas unitarias de LLM con xUnit y Semantic Kernel

Para los desarrolladores de .NET, la integración de la evaluación en el pipeline de CI/CD (GitHub Actions o Azure DevOps) es vital. Podemos utilizar frameworks de pruebas estándar como **xUnit** o **NUnit** para realizar pruebas de calidad de LLM.

Dado que no podemos comparar strings exactos (debido a la naturaleza generativa), utilizamos técnicas de aserción semántica.

#### Ejemplo de implementación: Test de Veracidad (Groundedness)

En este ejemplo, utilizaremos el SDK de **Semantic Kernel** para crear un test que evalúe si la respuesta de nuestro servicio RAG se mantiene fiel al contexto proporcionado.

```csharp
using Microsoft.SemanticKernel;
using Xunit;
using FluentAssertions;

public class RagEvaluationTests
{
    private readonly Kernel _kernel;

    public RagEvaluationTests()
    {
        // Inicializamos un Kernel específicamente para actuar como Juez
        var builder = Kernel.CreateBuilder();
        builder.AddAzureOpenAIChatCompletion("gpt-4o", "endpoint", "api-key");
        _kernel = builder.Build();
    }

    [Theory]
    [InlineData(
        "¿Cuál es la política de vacaciones?", 
        "Los empleados tienen 20 días al año.", 
        "Tienes 20 días de vacaciones anuales.")]
    [InlineData(
        "¿Cómo solicito un reembolso?", 
        "Usa el portal interno SAP.", 
        "Debes llamar por teléfono a recursos humanos.")] // Ejemplo que debería fallar en veracidad
    public async Task Evaluate_Groundedness_ShouldPassThreshold(string question, string context, string generatedAnswer)
    {
        // 1. Definimos el Prompt del Evaluador (Judge)
        string evaluationPrompt = @"
            Actúa como un auditor de calidad de IA. 
            Tu tarea es evaluar la VERACIDAD (Groundedness) de una respuesta basándote solo en el contexto.
            
            Contexto: {{$context}}
            Pregunta: {{$question}}
            Respuesta: {{$answer}}

            Puntúa de 1 a 5, donde 1 es 'inventado' y 5 es 'totalmente basado en el contexto'.
            Responde solo con el número.";

        // 2. Ejecutamos la evaluación
        var result = await _kernel.InvokePromptAsync(evaluationPrompt, new() {
            { "context", context },
            { "question", question },
            { "answer", generatedAnswer }
        });

        // 3. Aserción
        int score = int.Parse(result.ToString());
        score.Should().BeGreaterThanOrEqualTo(4, $"La respuesta para '{question}' no es veraz respecto al contexto.");
    }
}
```

### 5.1.4 Estrategias de Evaluación en el Ciclo de Vida de .NET

Para implementar un marco de evaluación completo, se deben considerar tres niveles de pruebas:

1.  **Unit Tests de Componentes (Deterministas):**
    *   Probar que el *Text Splitter* divide los documentos correctamente (sección 3.2.2).
    *   Probar que los filtros de metadatos de la base de datos vectorial funcionan.
    
2.  **Evaluación Basada en "Golden Datasets":**
    *   Se crea un archivo de referencia (Ground Truth) con el par `Pregunta -> Respuesta Correcta`.
    *   Se utiliza un "Evaluador de Similitud Coseno" o un LLM para medir qué tan cerca está la respuesta generada de la respuesta ideal.

3.  **Observabilidad con Application Insights:**
    *   Una vez desplegado (sección 5.3), se pueden capturar los "pulgares arriba/abajo" de los usuarios finales y correlacionarlos con los trazos de Semantic Kernel para identificar qué fragmentos de texto (chunks) están causando recuperaciones erróneas.

### 5.1.5 Herramientas complementarias para .NET

*   **Microsoft.ML.Tokenizers:** Permite validar si el contexto recuperado excede los límites de tokens antes de enviarlo al modelo, evitando errores de ejecución en los tests.
*   **DeepEval (vía Python Interop o API):** Aunque es nativo de Python, muchos equipos de .NET consumen sus métricas de *Hallucination Grade* a través de microservicios para integrarlos en sus tableros de control de calidad.

Al automatizar estos procesos, el equipo de desarrollo puede asegurar que los cambios en los prompts o en la estrategia de fragmentación (chunking) no degraden la calidad del sistema, permitiendo iteraciones rápidas y seguras.
