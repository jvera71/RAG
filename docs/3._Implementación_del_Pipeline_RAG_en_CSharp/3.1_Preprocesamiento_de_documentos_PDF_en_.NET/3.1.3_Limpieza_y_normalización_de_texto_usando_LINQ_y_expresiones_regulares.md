# 3.1.3 Limpieza y normalización de texto usando LINQ y expresiones regulares

Una vez que hemos logrado extraer el texto crudo de los documentos PDF (como vimos en las secciones 3.1.1 y 3.1.2), nos enfrentamos a un problema común: el texto resultante suele ser ruidoso. Los archivos PDF están diseñados para la visualización, no para el procesamiento de datos, lo que genera artefactos como saltos de línea inesperados, ligaduras de caracteres, números de página intercalados o múltiples espacios en blanco.

La **limpieza y normalización** es el proceso crítico para transformar ese ruido en un flujo de texto coherente. En el contexto de un sistema RAG, la calidad de la limpieza impacta directamente en la calidad de los *embeddings* y, por ende, en la precisión de la recuperación.

### 1. El uso de Expresiones Regulares (Regex) para la limpieza estructural

Las expresiones regulares en .NET son una herramienta extremadamente potente para identificar y corregir patrones repetitivos de ruido. En aplicaciones de alto rendimiento, es recomendable utilizar el atributo `[GeneratedRegex]` (introducido en .NET 7) para mejorar la eficiencia mediante generadores de código.

#### Eliminación de ruido común
El objetivo principal es eliminar elementos que no aportan valor semántico pero que consumen *tokens* innecesariamente.

```csharp
using System.Text.RegularExpressions;

public partial class TextCleaner
{
    // Eliminar múltiples espacios en blanco y tabulaciones
    [GeneratedRegex(@"[ \t]+")]
    private static partial Regex MultipleSpacesRegex();

    // Identificar saltos de línea repetitivos (más de dos seguidos)
    [GeneratedRegex(@"(\r?\n){3,}")]
    private static partial Regex ExcessiveLineBreaksRegex();

    // Detectar patrones de pies de página o encabezados comunes (ej: "Página 1 de 10")
    [GeneratedRegex(@"Página \d+ de \d+", RegexOptions.IgnoreCase)]
    private static partial Regex PaginationRegex();

    public static string CleanBasicNoise(string input)
    {
        if (string.IsNullOrWhiteSpace(input)) return string.Empty;

        // Aplicar transformaciones
        var result = PaginationRegex().Replace(input, "");
        result = MultipleSpacesRegex().Replace(result, " ");
        result = ExcessiveLineBreaksRegex().Replace(result, Environment.NewLine + Environment.NewLine);

        return result.Trim();
    }
}
```

#### Corrección de la rotura de palabras (Hyphenation)
Un artefacto muy común en PDFs es la división de palabras al final de una línea mediante un guion. Si no se limpia, el modelo de embeddings tratará "inteli-gencia" como dos palabras distintas o una palabra inexistente.

```csharp
// Une palabras cortadas por guion al final de una línea
[GeneratedRegex(@"(\w+)-\s*\r?\n\s*(\w+)")]
private static partial Regex HyphenatedWordRegex();

public static string FixHyphenation(string input)
{
    return HyphenatedWordRegex().Replace(input, "$1$2");
}
```

### 2. Normalización y Filtrado con LINQ

Mientras que Regex es ideal para patrones complejos, **LINQ (Language Integrated Query)** es la herramienta preferida para la manipulación a nivel de colección de líneas o caracteres, permitiendo una sintaxis declarativa y fácil de mantener.

#### Filtrado de líneas irrelevantes
A menudo, después de extraer el texto, quedan líneas que consisten únicamente en caracteres especiales, símbolos de viñetas o fragmentos demasiado cortos que solo añaden ruido al fragmento (*chunk*).

```csharp
public static string FilterIrrelevantLines(string text)
{
    var lines = text.Split(new[] { "\r\n", "\r", "\n" }, StringSplitOptions.None);

    var cleanLines = lines
        .Select(line => line.Trim())
        // Filtrar líneas que son solo números (ej. numeración de tablas) o muy cortas
        .Where(line => line.Length > 3 && !line.All(c => char.IsDigit(c) || char.IsPunctuation(c)))
        .ToList();

    return string.Join(Environment.NewLine, cleanLines);
}
```

#### Normalización de caracteres (Unicode)
Los PDFs suelen contener caracteres especiales o formatos Unicode que pueden confundir a ciertos tokenizadores. Podemos usar LINQ para normalizar el texto a una forma canónica (Form C o Form D) y filtrar caracteres no deseados.

```csharp
public static string NormalizeText(string input)
{
    // Normalización Unicode para manejar tildes y caracteres compuestos
    string normalized = input.Normalize(System.Text.NormalizationForm.FormC);

    // Filtrar caracteres de control no imprimibles (excepto saltos de línea y tabs)
    var filteredChars = normalized
        .Where(c => !char.IsControl(c) || c == '\n' || c == '\r' || c == '\t')
        .ToArray();

    return new string(filteredChars);
}
```

### 3. Pipeline de Limpieza Integrado

En un flujo RAG profesional, estas operaciones se encadenan. Es importante el orden: primero la limpieza de caracteres, luego la estructural (Regex) y finalmente el filtrado lógico (LINQ).

```csharp
public string PrepareTextForEmbedding(string rawText)
{
    return rawText
        .Pipe(NormalizeText)
        .Pipe(FixHyphenation)
        .Pipe(CleanBasicNoise)
        .Pipe(FilterIrrelevantLines);
}

// Método de extensión simple para legibilidad (Fluent API)
public static class ProcessingExtensions
{
    public static string Pipe(this string input, Func<string, string> func) => func(input);
}
```

### Por qué es vital este paso para RAG en .NET
1.  **Ahorro de costos:** Al eliminar espacios, encabezados y pies de página redundantes, reducimos el número total de tokens enviados a los modelos de OpenAI o Anthropic.
2.  **Densidad de información:** Un fragmento de texto limpio permite que el modelo de *embedding* capture mejor el significado semántico real sin interferencias de caracteres de control o saltos de línea mal posicionados.
3.  **Consistencia de búsqueda:** Si el usuario busca "inteligencia" y en el vector de la base de datos está guardado como "inteli- gencia", la similitud de coseno disminuirá drásticamente, fallando en recuperar el contexto relevante.

Esta fase de limpieza prepara el terreno para la **Detección de Idioma (3.1.4)** y, más adelante, para la **Estrategia de Fragmentación (3.2)**, donde el texto ya normalizado será dividido en unidades lógicas con sentido completo.
