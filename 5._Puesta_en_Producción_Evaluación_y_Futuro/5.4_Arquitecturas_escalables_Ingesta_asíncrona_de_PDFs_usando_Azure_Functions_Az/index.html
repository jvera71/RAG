    5.4 Arquitecturas escalables: Ingesta asíncrona de PDFs usando Azure Functions, Azure Event Grid o RabbitMQ

    En las secciones anteriores hemos analizado cómo procesar un PDF, fragmentarlo y generar embeddings. Sin embargo, en un entorno de producción, realizar estas tareas de forma sincrónica dentro del ciclo de vida de una solicitud HTTP (por ejemplo, en un controlador de ASP.NET Core) es inviable. El procesamiento de documentos, especialmente si involucra OCR o modelos de embeddings pesados, puede tardar desde segundos hasta minutos, superando los tiempos de espera (timeouts) y degradando la experiencia del usuario.

    La ingesta asíncrona desacopla la carga del documento de su procesamiento, permitiendo que el sistema escale horizontalmente y sea resiliente ante fallos.

    5.4.1 El Patrón de Desacoplamiento (Producer-Consumer)

    Para lograr una arquitectura escalable, debemos separar la API que recibe el archivo del motor que lo procesa. El flujo típico sigue este patrón:

    1. Carga (Upload): El cliente envía el PDF a una API.
    2. Persistencia: La API guarda el archivo en un almacenamiento persistente (ej. Azure Blob Storage o un sistema de archivos local).
    3. Mensajería: La API publica un mensaje o evento indicando que hay un nuevo documento pendiente.
    4. Procesamiento: Un trabajador (worker) independiente consume el mensaje, descarga el PDF y ejecuta el pipeline RAG definido en el Capítulo 3.

    A["💻 Cliente (Subir PDF)"] --> B["🌐 ASP.NET Core API"]
    B -->|1. Guarda Archivo| C["🪣 Azure Blob Storage"]
    B -->|2. Encola Mensaje| D["📥 Azure Storage Queue / RabbitMQ"]

    D -->|3. Trigger de Evento| E["⚡ Worker Service / Azure Function"]
    E -->|4. Descarga PDF| C
    E -->|5. Procesa, fragmenta e indexa| F[("🗄️ Azure AI Search / Qdrant")]

    5.4.2 Implementación con Azure Functions y Azure Event Grid

    Azure ofrece un enfoque serverless altamente escalable. En este escenario, el desencadenante de la ingesta no es una llamada directa, sino un evento en el almacenamiento.

    Flujo de trabajo: 1. La aplicación .NET sube el PDF a un contenedor de Azure Blob Storage. 2. Azure Event Grid detecta la creación del blob y dispara un evento. 3. Una Azure Function con un EventGridTrigger o BlobTrigger se activa automáticamente para procesar el documento.

    Ejemplo de Azure Function (Worker):

    using System;
using System.IO;
using System.Threading.Tasks;
using Microsoft.Azure.Functions.Worker;
using Microsoft.Extensions.Logging;

public class DocumentIngestionWorker
{
    private readonly IEmbeddingService _embeddingService; // Definido en Cap. 2.5
    private readonly IPdfProcessor _pdfProcessor;         // Definido en Cap. 3.1
    private readonly IVectorDatabase _vectorDb;           // Definido en Cap. 2.5.2

    public DocumentIngestionWorker(IEmbeddingService embeddingService, IPdfProcessor pdfProcessor, IVectorDatabase vectorDb)
    {
        _embeddingService = embeddingService;
        _pdfProcessor = pdfProcessor;
        _vectorDb = vectorDb;
    }

    [Function("ProcessPdfOnUpload")]
    public async Task Run([BlobTrigger("ingestion-folder/{name}", Connection = "AzureWebJobsStorage")] Stream pdfStream, string name, FunctionContext context)
    {
        var logger = context.GetLogger("ProcessPdfOnUpload");
        logger.LogInformation($"Procesando archivo: {name}");

        try
        {
            // 1. Extracción y limpieza (Capítulo 3.1)
            var text = await _pdfProcessor.ExtractTextAsync(pdfStream);

            // 2. Fragmentación (Chunking) (Capítulo 3.2)
            var chunks = _pdfProcessor.SplitIntoChunks(text);

            // 3. Generación de Embeddings y Carga en Vector DB (Capítulo 2.5 y 2.6)
            foreach (var chunk in chunks)
            {
                var embedding = await _embeddingService.GetEmbeddingsAsync(chunk);
                await _vectorDb.UpsertVectorAsync(embedding, metadata: new { FileName = name, Content = chunk });
            }

            logger.LogInformation($"Archivo {name} indexado correctamente.");
        }
        catch (Exception ex)
        {
            logger.LogError($"Error procesando {name}: {ex.Message}");
            // Aquí se podría mover a una "Dead Letter Queue" para reintentos
            throw;
        }
    }
}

    5.4.3 Implementación con RabbitMQ y Worker Services

    En entornos on-premise o nubes híbridas, RabbitMQ es la opción preferida para gestionar colas de mensajería robustas. Aquí, utilizaremos un .NET Worker Service (BackgroundService) para procesar las tareas.

    Configuración del Productor (ASP.NET Core API): La API no procesa el PDF; simplemente lo guarda y publica un mensaje con el ID o la ruta del documento.

    [HttpPost("upload")]
public async Task<IActionResult> UploadPdf(IFormFile file)
{
    // Guardar archivo en storage y obtener 'fileId'
    var fileId = await _storageService.SaveAsync(file.OpenReadStream(), file.FileName);

    // Publicar mensaje en RabbitMQ
    var message = new { DocumentId = fileId, Timestamp = DateTime.UtcNow };
    _bus.Publish("pdf_ingestion_queue", message);

    return Accepted(new { Id = fileId, Status = "En procesamiento" });
}

    Configuración del Consumidor (Worker Service): Este servicio corre de forma independiente y puede escalarse mediante contenedores (Docker/Kubernetes).

    public class IngestionBackgroundWorker : BackgroundService
{
    private readonly IModel _channel; // RabbitMQ Channel
    private readonly IServiceProvider _serviceProvider;

    protected override Task ExecuteAsync(CancellationToken stoppingToken)
    {
        var consumer = new EventingBasicConsumer(_channel);
        consumer.Received += async (model, ea) =>
        {
            using var scope = _serviceProvider.CreateScope();
            var processor = scope.ServiceProvider.GetRequiredService<IPdfIngestionPipeline>();

            var body = ea.Body.ToArray();
            var message = JsonSerializer.Deserialize<IngestionMessage>(body);

            await processor.ExecuteAsync(message.DocumentId); // Ejecuta el pipeline RAG

            _channel.BasicAck(ea.DeliveryTag, false);
        };

        _channel.BasicConsume(queue: "pdf_ingestion_queue", autoAck: false, consumer: consumer);
        return Task.CompletedTask;
    }
}

    5.4.4 Consideraciones Críticas para la Escalabilidad

    1. Idempotencia: Dado que los sistemas de mensajería pueden entregar un mensaje más de una vez (entrega at-least-once), el pipeline de ingesta debe ser capaz de manejar duplicados sin corromper la base de datos vectorial. Se recomienda usar el hash del contenido del documento como ID en la base vectorial.
    2. Manejo de Reintentos y DLQ (Dead Letter Queues): Si un documento falla (por ejemplo, por un error de red con el modelo de embeddings), el mensaje debe moverse a una cola de errores después de N reintentos para su inspección manual o reprocesamiento automático.
    3. Backpressure (Contrapresión): Al usar RabbitMQ o colas de Azure Service Bus, el sistema protege a los modelos de IA de una sobrecarga. Si se suben 1,000 PDFs de golpe, la cola actuará como un amortiguador, procesándolos según la capacidad disponible de los workers.
    4. Escalado Basado en Eventos (KEDA): Si se utiliza Kubernetes, se puede usar KEDA (Kubernetes-based Event-Driven Autoscaling) para escalar el número de pods de procesamiento en función de la profundidad de la cola de RabbitMQ o Azure Service Bus.

    Esta arquitectura asíncrona garantiza que, independientemente del volumen de documentos, la aplicación principal permanezca receptiva y los recursos de computación se utilicen de manera eficiente.
