# 2.8 Consideraciones de Seguridad y Privacidad en entornos empresariales (*Autenticación con Entra ID, RBAC en Azure*)

## 2.8 Consideraciones de Seguridad y Privacidad en entornos empresariales

Al implementar sistemas de Generación Aumentada por Recuperación (RAG) en entornos corporativos, la seguridad no es una característica opcional, sino un requisito fundamental. A diferencia de las aplicaciones de consumo general, las soluciones empresariales manejan datos sensibles, propiedad intelectual y documentos privados que no deben filtrarse fuera de los límites de la organización o entre departamentos no autorizados.

En el ecosistema .NET y Azure, la seguridad se aborda mediante un enfoque de **Defensa en Profundidad**, centrándose principalmente en la identidad, el acceso granular a los datos y la protección de la infraestructura.

### 2.8.1 Autenticación Moderna con Microsoft Entra ID

El uso de claves de API (API Keys) estáticas en archivos de configuración es una práctica de alto riesgo en producción. En su lugar, las aplicaciones .NET deben utilizar **Microsoft Entra ID** (anteriormente Azure Active Directory) para una autenticación basada en identidades.

Para aplicaciones RAG desplegadas en Azure (como App Services o Azure Functions), la mejor práctica es el uso de **Managed Identities** (Identidades Administradas). Esto permite que el código .NET se autentique contra servicios como Azure OpenAI o Azure AI Search sin necesidad de gestionar credenciales en el código o en variables de entorno.

#### Ejemplo de implementación con `Azure.Identity`

En C#, podemos utilizar la librería `Azure.Identity` para obtener un token de forma transparente:

```csharp
using Azure.Identity;
using Azure.AI.OpenAI;
using Microsoft.Extensions.Configuration;

// Configuración del cliente utilizando DefaultAzureCredential
// Esta clase intentará autenticarse usando Managed Identity, 
// variables de entorno o la sesión iniciada en Visual Studio/Azure CLI.
var client = new OpenAIClient(
    new Uri("https://tu-recurso-openai.openai.azure.com/"),
    new DefaultAzureCredential());

// A partir de aquí, el cliente está autenticado sin haber usado una API Key
```

### 2.8.2 Control de Acceso Basado en Roles (RBAC) en Azure

Una vez que la identidad está establecida, debemos aplicar el principio de **mínimo privilegio** mediante RBAC. No basta con que la aplicación pueda "entrar"; debe tener permisos específicos solo para lo que necesita.

En un pipeline RAG típico, los roles comunes que debemos configurar son:

*   **Cognitive Services OpenAI User:** Permite realizar inferencias y generar embeddings, pero no administrar el recurso.
*   **Search Index Data Reader:** Permite realizar consultas de búsqueda sobre el índice vectorial en Azure AI Search.
*   **Search Index Data Contributor:** Utilizado por el pipeline de ingesta (sección 2.6) para escribir y actualizar los fragmentos de documentos.
*   **Storage Blob Data Reader:** Si los PDFs originales se almacenan en Azure Blob Storage.

### 2.8.3 Seguridad a nivel de documento (Document-Level Security)

Uno de los mayores desafíos en RAG empresarial es garantizar que un usuario solo reciba respuestas basadas en documentos a los que tiene permiso de lectura. Si el sistema recupera información de un PDF de "Recursos Humanos" para responder a un empleado de "Ventas" que no tiene acceso a dicho archivo, se produce una brecha de seguridad.

Para solucionar esto en .NET, implementamos **Filtros de Seguridad** en la fase de recuperación (Retrieval):

1.  **Metadatos de Acceso:** Durante la ingesta (sección 3.2), se almacenan los identificadores de grupo o usuarios autorizados (provenientes de Entra ID) como metadatos en cada fragmento (chunk) dentro de la base de datos vectorial.
2.  **Filtrado en tiempo de ejecución:** Al realizar la búsqueda vectorial, se añade un filtro OData o SQL que restringe los resultados a los fragmentos donde el usuario actual tenga permisos.

```csharp
// Ejemplo conceptual de búsqueda con filtro de seguridad en Azure AI Search
var searchOptions = new SearchOptions
{
    // Supongamos que obtenemos los grupos del usuario desde sus Claims de Identity
    Filter = "allowed_groups/any(g: search.in(g, 'finance-dept, legal-team'))",
    Size = 5
};

// La búsqueda solo devolverá fragmentos que coincidan con los grupos del usuario
var response = await searchClient.SearchAsync<SearchDocument>("query vectorial", searchOptions);
```

### 2.8.4 Privacidad de Datos y Residencia

Al trabajar con LLMs, surge la preocupación de si los datos enviados se utilizarán para reentrenar los modelos globales. En el caso de **Azure OpenAI**, existe una garantía contractual de que:

*   Los datos del cliente **no** se utilizan para entrenar los modelos base de OpenAI.
*   Los datos están protegidos por los estándares de cumplimiento de Azure (ISO, SOC, HIPAA).
*   Es posible habilitar el "Filtrado de Contenido" para evitar que el modelo genere salidas tóxicas o procese entradas malintencionadas (Prompt Injection).

### 2.8.5 Conectividad Privada (Private Link)

Para una seguridad máxima, las aplicaciones RAG en .NET no deben comunicarse con los servicios de IA a través de la internet pública. Se recomienda el uso de **Azure Private Endpoints**. Esto garantiza que el tráfico entre el servidor de aplicaciones .NET y la base de datos vectorial o el servicio de embeddings viaje exclusivamente por la red virtual (VNET) privada de la empresa, mitigando ataques de interceptación y exposición de datos.
