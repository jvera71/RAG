# 3.2.1 Impacto de la división de texto (*Text Splitting / Chunking*) en la calidad de RAG

### 3.2.1 Impacto de la división de texto (*Text Splitting / Chunking*) en la calidad de RAG

Una vez que hemos extraído con éxito el texto de nuestros documentos PDF (tal como se abordó en el apartado 3.1), nos enfrentamos a un desafío crítico: el texto extraído suele ser demasiado extenso para ser procesado como una sola unidad por un Modelo de Lenguaje Grande (LLM). Aquí es donde entra en juego el **Chunking** o división de texto.

El *chunking* es el proceso de fragmentar el texto en piezas más pequeñas y semánticamente significativas. No es simplemente un paso técnico de preprocesamiento, sino que es uno de los pilares que determina la precisión y la utilidad de todo el sistema RAG.

#### La relevancia del Chunking en la arquitectura RAG

El tamaño y la estrategia de fragmentación impactan directamente en dos etapas fundamentales:

1.  **En la Recuperación (Retrieval):** Las bases de datos vectoriales almacenan *embeddings* de estos fragmentos. Si un fragmento es demasiado grande, su representación vectorial será muy genérica ("diluida"), dificultando que el algoritmo de búsqueda encuentre coincidencias precisas. Si es demasiado pequeño, puede carecer de la información necesaria para que el modelo de búsqueda entienda su significado real.
2.  **En la Generación (Synthesis):** El LLM recibe los fragmentos recuperados como contexto. Fragmentos mal divididos pueden cortar oraciones por la mitad o separar un dato numérico de su unidad de medida, entregando información incompleta o incoherente al modelo generativo.

#### Factores de impacto en la calidad

Para diseñar una estrategia de fragmentación efectiva en .NET, debemos considerar los siguientes factores:

*   **Límites de Contexto (Context Window):** Aunque modelos modernos soportan ventanas de contexto extensas, enviar fragmentos innecesariamente grandes aumenta la latencia y el costo por token.
*   **Densidad Semántica:** Un fragmento ideal debe contener una idea completa. Por ejemplo, en un manual técnico de un motor, un fragmento debería cubrir un paso específico del mantenimiento, no medio paso del motor y medio paso del sistema eléctrico.
*   **Ruido vs. Señal:** Si los fragmentos son muy grandes, el LLM puede distraerse con información irrelevante incluida en el fragmento (ruido), lo que degrada la calidad de la respuesta final.

#### Representación de datos en C#

Desde una perspectiva de ingeniería de software en .NET, un fragmento no es solo una `string`. Para mantener la trazabilidad y la calidad, solemos representar los fragmentos como objetos enriquecidos. A continuación, se muestra una estructura típica que prepara el terreno para la indexación:

```csharp
public class TextChunk
{
    public string Id { get; set; } = Guid.NewGuid().ToString();
    public string Content { get; set; } // El texto fragmentado
    public int TokenCount { get; set; } // Calculado con Microsoft.ML.Tokenizers
    
    // Metadatos cruciales para la recuperación y reconstrucción
    public Metadata Info { get; set; }

    public class Metadata
    {
        public string SourceDocument { get; set; }
        public int PageNumber { get; set; }
        public int ChunkIndex { get; set; }
        public string SectionTitle { get; set; } // Si se detectó en 3.1.6
    }
}
```

#### El problema del "Solapamiento" (Overlap)

Para mitigar la pérdida de contexto semántico en los bordes de cada fragmento, se utiliza la técnica de **Overlap** (solapamiento). Esto implica que el final del fragmento *N* se repite al inicio del fragmento *N+1*.

*   **Impacto de un solapamiento bajo:** Riesgo de fragmentar conceptos que dependen de la frase anterior.
*   **Impacto de un solapamiento alto:** Aumento de la redundancia en los resultados recuperados, lo que consume más ventana de contexto del LLM sin aportar información nueva.

#### Ejemplo conceptual de impacto en la búsqueda

Imagine que el PDF dice: *"El sensor de temperatura debe calibrarse cada 6 meses. Sin embargo, en ambientes corrosivos, este periodo debe reducirse a 2 meses."*

*   **Escenario A (Sin solapamiento, chunk pequeño):**
    *   Chunk 1: "El sensor de temperatura debe calibrarse cada 6 meses."
    *   Chunk 2: "Sin embargo, en ambientes corrosivos, este periodo debe reducirse a 2 meses."
    *   **Resultado:** Si el usuario pregunta "¿Cada cuánto se calibra el sensor en ambientes corrosivos?", el sistema podría recuperar solo el Chunk 2. Al no saber a qué se refiere "este periodo", el LLM podría alucinar o dar una respuesta vaga.

*   **Escenario B (Con solapamiento adecuado):**
    *   Chunk 1: "...calibrarse cada 6 meses."
    *   Chunk 2: "calibrarse cada 6 meses. Sin embargo, en ambientes corrosivos, este periodo..."
    *   **Resultado:** El vector del Chunk 2 ahora contiene suficiente contexto semántico para ser identificado correctamente y permite al LLM generar una respuesta precisa.
