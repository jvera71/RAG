# 5.3 Monitoreo y Observabilidad (*Integración con Application Insights y OpenTelemetry en .NET*)

### 5.3 Monitoreo y Observabilidad: Integración con Application Insights y OpenTelemetry en .NET

En un sistema RAG (Generación Aumentada por Recuperación), la observabilidad no es solo una cuestión de saber si el servicio está "vivo" o "caído". Debido a la naturaleza estocástica de los LLMs y la complejidad de las cadenas de recuperación, necesitamos visibilidad sobre la latencia de cada fragmento (chunk), el costo en tokens, la precisión de la base de datos vectorial y el rendimiento de las llamadas a la API del modelo.

En el ecosistema .NET, el estándar de oro para lograr esto es **OpenTelemetry (OTel)** combinado con **Azure Application Insights**.

#### 1. El Rol de OpenTelemetry en RAG

OpenTelemetry proporciona un marco neutral para la recolección de trazas, métricas y registros. En una arquitectura RAG construida con **Semantic Kernel** o el SDK de **Azure OpenAI**, muchas de las instrumentaciones ya vienen integradas, permitiéndonos rastrear:

*   **Trazas distribuidas:** Ver el flujo completo desde que el usuario hace una pregunta hasta que el sistema recupera fragmentos del PDF y genera una respuesta.
*   **Métricas de rendimiento:** Latencia de la búsqueda vectorial (ej. en Qdrant o Azure AI Search) vs. latencia de generación del LLM.
*   **Consumo de Tokens:** Seguimiento detallado de *Prompt Tokens* y *Completion Tokens* para control de costos.

#### 2. Configuración de la Instrumentación en .NET

Para integrar el monitoreo en nuestra aplicación RAG, primero debemos configurar el SDK de OpenTelemetry en el archivo `Program.cs`.

```csharp
using Azure.Monitor.OpenTelemetry.AspNetCore;
using OpenTelemetry.Logs;
using OpenTelemetry.Metrics;
using OpenTelemetry.Resources;
using OpenTelemetry.Trace;

var builder = WebApplication.CreateBuilder(args);

// Configuración de OpenTelemetry para Azure Application Insights
builder.Services.AddOpenTelemetry()
    .UseAzureMonitor() // Simplifica la conexión con App Insights
    .WithTracing(tracing =>
    {
        tracing.AddSource("Microsoft.SemanticKernel*") // Captura trazas de Semantic Kernel
               .AddSource("Azure.AI.OpenAI*")          // Captura trazas del SDK de OpenAI
               .AddHttpClientInstrumentation()         // Monitorea llamadas HTTP a bases vectoriales
               .AddAspNetCoreInstrumentation();
    })
    .WithMetrics(metrics =>
    {
        metrics.AddMeter("Microsoft.SemanticKernel*")
               .AddAspNetCoreInstrumentation()
               .AddHttpClientInstrumentation();
    });

var app = builder.Build();
```

#### 3. Monitoreo del Pipeline de Recuperación (Retrieval)

Es crítico medir cuánto tiempo toma la fase de búsqueda en comparación con la de generación. Si la recuperación de fragmentos del PDF tarda 2 segundos y la generación 1 segundo, el cuello de botella está en nuestra base de datos vectorial o en el proceso de embedding.

Podemos crear actividades personalizadas para medir pasos específicos del pipeline RAG:

```csharp
using System.Diagnostics;

public class RagService
{
    private static readonly ActivitySource _activitySource = new("MyRagApp.Engine");

    public async Task<string> GetAnswerAsync(string query)
    {
        using var activity = _activitySource.StartActivity("RAG_Full_Cycle");

        // 1. Paso de Recuperación
        using (var retrievalSpan = _activitySource.StartActivity("Vector_Search"))
        {
            var context = await _vectorDb.SearchAsync(query);
            retrievalSpan?.SetTag("docs_retrieved", context.Count);
        }

        // 2. Paso de Generación
        using (var generationSpan = _activitySource.StartActivity("LLM_Generation"))
        {
            var result = await _kernel.InvokeAsync(prompt, new { input = query });
            return result.ToString();
        }
    }
}
```

#### 4. Seguimiento de Tokens y Costos

Uno de los mayores desafíos en producción es el costo. Application Insights permite visualizar las dimensiones personalizadas enviadas por los SDKs de IA.

Cuando utilizamos `Semantic Kernel`, este emite automáticamente eventos que incluyen el conteo de tokens. En el portal de Azure, podemos realizar consultas en **Log Analytics (Kusto - KQL)** para analizar el consumo:

```kusto
dependencies
| where target contains "openai.azure.com"
| extend tokens_used = parse_json(customDimensions).["gen_ai.usage.total_tokens"]
| summarize AvgTokens = avg(todouble(tokens_used)), MaxTokens = max(todouble(tokens_used)) by operation_Name
```

#### 5. Observabilidad de la Calidad (Fidelidad y Relevancia)

Más allá de las métricas técnicas, debemos monitorear la "salud" de las respuestas. Podemos utilizar **Custom Properties** en Application Insights para marcar interacciones que el usuario califique como útiles o erróneas (feedback loop):

```csharp
public void TrackUserFeedback(string traceId, bool isPositive)
{
    var telemetryClient = new TelemetryClient(); // Inyectado vía DI
    var evt = new EventTelemetry("RAG_User_Feedback");
    evt.Properties.Add("TraceId", traceId);
    evt.Properties.Add("Feedback", isPositive ? "Positive" : "Negative");
    telemetryClient.TrackEvent(evt);
}
```

#### 6. Dashboarding y Alertas

Con los datos fluyendo hacia Application Insights, el siguiente paso en la puesta en producción es la creación de dashboards en Azure que muestren:
1.  **P95 Latency:** El tiempo que el 95% de los usuarios espera por una respuesta.
2.  **Token Burn Rate:** Gasto acumulado diario/mensual.
3.  **Error Rate por Modelo:** Comparar si `gpt-4` falla más o menos que `gpt-3.5-turbo` en tareas de extracción de datos del PDF.
4.  **Vector DB Latency:** Tiempo de respuesta del servicio de búsqueda (crucial cuando el corpus de PDFs crece a miles de documentos).

Esta infraestructura de observabilidad permite que el paso de un prototipo a una solución empresarial sea seguro, permitiendo iterar el prompt engineering (visto en la sección 3.3) o el chunking (sección 3.2) basándose en datos reales y no en intuiciones.
