# 3.2.3 Impacto de los metadatos en la base de datos vectorial

En el desarrollo de un pipeline de RAG (Generación Aumentada por Recuperación), la tentación inicial es centrarse exclusivamente en los *embeddings* (la representación vectorial del texto). Sin embargo, el almacenamiento de metadatos asociados a esos vectores es lo que transforma una simple búsqueda de similitud en un sistema de recuperación robusto, preciso y auditable para aplicaciones empresariales en .NET.

### ¿Qué son los Metadatos en una Base de Datos Vectorial?

Los metadatos son atributos estructurados (pares clave-valor) que se almacenan junto al vector de características y el fragmento de texto original (*chunk*). Mientras que el vector permite realizar búsquedas por "significado semántico", los metadatos permiten realizar búsquedas por "hechos" o "propiedades".

En el contexto de procesamiento de PDFs que estamos abordando, los metadatos esenciales suelen incluir:
*   **Identificadores de origen:** Nombre del archivo, URL o ID del documento en el CMS.
*   **Localización física:** Número de página, sección o coordenadas (si se usó OCR en el punto 3.1.5).
*   **Atributos temporales:** Fecha de creación, última modificación o versión del documento.
*   **Clasificación:** Departamento, categoría del documento (ej. "Contratos", "Manuales Técnicos") o nivel de seguridad.

### El Impacto Crítico en el Pipeline RAG

El uso estratégico de metadatos impacta tres áreas fundamentales de nuestra arquitectura .NET:

#### 1. Filtrado de Consultas (Pre-filtering y Post-filtering)
La búsqueda puramente semántica puede fallar si el corpus es muy grande. Los metadatos permiten aplicar filtros antes de realizar la comparación de vectores. 
*   **Ejemplo:** Si un usuario pregunta "¿Qué dice mi contrato sobre la rescisión?", el sistema no debería buscar en todos los contratos de la empresa, sino pre-filtrar por el metadato `ClientId == "12345"`. Esto reduce drásticamente el ruido y mejora la latencia.

#### 2. Atribución y Citación (Grounding)
Uno de los mayores problemas de los LLMs son las alucinaciones. Al recuperar los metadatos junto con el texto, podemos inyectar en el prompt instrucciones para que el modelo cite la fuente: *"Basándote en la página 14 del archivo 'Seguridad_v2.pdf'..."*. Sin metadatos, el usuario final recibe una respuesta, pero no tiene forma de verificar su veracidad.

#### 3. Control de Acceso (RBAC)
En entornos corporativos (mencionado en el punto 2.8), no todos los usuarios deben ver todos los documentos. Almacenar metadatos como `AllowedRoles: ["HR_Manager", "Admin"]` permite que la capa de datos de .NET filtre los resultados en tiempo de ejecución, asegurando que el motor de búsqueda vectorial solo devuelva fragmentos a los que el usuario tiene acceso legítimo.

### Implementación en C# con .NET

Para gestionar estos metadatos, es una buena práctica definir un modelo de datos que represente nuestro registro en la base de datos vectorial (como Azure AI Search, Qdrant o Milvus).

A continuación, se muestra un ejemplo de cómo estructurar un registro utilizando atributos de **Semantic Kernel** o un enfoque genérico para bases vectoriales:

```csharp
public class DocumentChunk
{
    // El ID único del fragmento
    public string Id { get; set; } = Guid.NewGuid().ToString();

    // El contenido de texto procesado en el punto 3.1 y 3.2.2
    public string Text { get; set; }

    // El vector generado por el modelo de embeddings (Azure OpenAI / ONNX)
    public ReadOnlyMemory<float> Vector { get; set; }

    // --- SECCIÓN DE METADATOS ---
    public string FileName { get; set; }
    public int PageNumber { get; set; }
    public string Category { get; set; }
    public DateTime LastModified { get; set; }
    public string DocumentSecurityLevel { get; set; }
}
```

#### Ejemplo de Recuperación con Filtrado por Metadatos

Si estamos utilizando el SDK de **Azure AI Search** en C#, el impacto de los metadatos se traduce en la capacidad de ejecutar consultas híbridas filtradas:

```csharp
using Azure.Search.Documents;
using Azure.Search.Documents.Models;

public async Task<List<DocumentChunk>> SearchContractAsync(float[] queryVector, string clientId)
{
    var searchOptions = new SearchOptions
    {
        // Aplicamos un filtro basado en metadatos ANTES de la búsqueda vectorial
        Filter = $"ClientId eq '{clientId}'", 
        VectorQueries = { new VectorizedQuery(queryVector) { KNearestNeighborsCount = 3, Fields = { "Vector" } } },
        Select = { "Text", "FileName", "PageNumber" } // Recuperamos metadatos para la respuesta
    };

    var response = await _searchClient.SearchAsync<DocumentChunk>(null, searchOptions);
    
    // El resultado incluye el texto para el LLM y los metadatos para la interfaz de usuario
    return response.Value.GetResults().Select(r => r.Document).ToList();
}
```

### Consideraciones Técnicas y de Rendimiento

1.  **Cardinalidad:** Tenga cuidado con metadatos de alta cardinalidad (como IDs de transacción únicos) si su base de datos vectorial no los indexa eficientemente.
2.  **Sincronización:** Si el documento original en el PDF cambia o se elimina, los metadatos en la base de datos vectorial deben actualizarse. En el punto 5.4 exploraremos cómo las *Azure Functions* ayudan a mantener esta coherencia.
3.  **Overhead:** Almacenar demasiado texto o metadatos innecesarios en la base de datos vectorial puede aumentar los costos de almacenamiento. Lo ideal es guardar solo lo necesario para el filtrado y la reconstrucción de la respuesta, manteniendo el documento completo en un *Blob Storage* si es necesario.

En conclusión, los metadatos no son información "adicional" u opcional; son el mecanismo que permite que un sistema RAG pase de ser un experimento de laboratorio a una herramienta empresarial fiable, permitiendo filtrado preciso, cumplimiento normativo y una experiencia de usuario donde cada respuesta de la IA está debidamente respaldada por una referencia documental.
