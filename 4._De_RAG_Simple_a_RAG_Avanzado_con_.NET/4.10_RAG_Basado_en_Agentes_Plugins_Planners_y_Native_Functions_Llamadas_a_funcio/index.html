    4.10 RAG Basado en Agentes: Plugins, Planners y Native Functions (Llamadas a funciones) en Semantic Kernel

    En el punto 4.10, elevamos la arquitectura de RAG de un flujo lineal y estático (recuperar -> aumentar -> generar) a un sistema dinámico y autónomo. El RAG Basado en Agentes utiliza a los LLMs no solo como generadores de texto, sino como motores de razonamiento capaces de interactuar con el entorno mediante herramientas externas.

    En el ecosistema .NET, Semantic Kernel (SK) es el orquestador líder para construir estos agentes. A continuación, desglosamos los componentes que permiten convertir un pipeline de RAG tradicional en un sistema agéntico.

    4.10.1 El concepto de Agente en RAG

    A diferencia del RAG simple, donde el programador define exactamente qué base de datos vectorial consultar, un agente puede decidir: 1. Si necesita o no consultar documentos externos. 2. Qué herramienta (Plugin) es la más adecuada para la consulta actual. 3. Evaluar si la información recuperada es suficiente o si debe realizar una segunda búsqueda con términos diferentes.

    4.10.2 Native Functions: El "Cuerpo" del Agente

    Las Native Functions son métodos de C# que el LLM puede invocar. En el contexto de RAG, estas funciones suelen encapsular la lógica de búsqueda en bases de datos vectoriales o el procesamiento de datos extraídos de los PDFs que vimos en el Capítulo 3.

    Para que una función sea accesible por el agente, debe decorarse con el atributo KernelFunction.

    public class SearchPlugin
{
    private readonly IVectorDbService _vectorDb;

    public SearchPlugin(IVectorDbService vectorDb) => _vectorDb = vectorDb;

    [KernelFunction, Description("Busca información técnica sobre especificaciones de productos en el manual PDF.")]
    public async Task<string> SearchProductSpecs(
        [Description("El término de búsqueda o pregunta técnica")] string query)
    {
        // Aquí se integra la lógica de búsqueda vectorial (ver sección 2.5)
        var results = await _vectorDb.SearchAsync(query);
        return string.Join("\n", results);
    }
}

    4.10.3 Plugins: Agrupación Lógica de Capacidades

    Un Plugin en Semantic Kernel es una colección de funciones (tanto nativas de C# como de tipo Prompt). En una arquitectura RAG avanzada, podrías tener múltiples plugins: - PdfSearchPlugin: Para búsqueda semántica en documentos. - CalculatorPlugin: Para realizar cálculos precisos sobre los datos numéricos extraídos (evitando alucinaciones matemáticas del LLM). - DatabasePlugin: Para consultar datos transaccionales en tiempo real vía Entity Framework.

    4.10.4 Function Calling (Llamadas a funciones) automático

    Esta es la pieza clave del RAG agéntico. Los modelos modernos (como GPT-4o o modelos locales vía ONNX) pueden devolver una "solicitud de llamada a función" en lugar de texto. Semantic Kernel intercepta esto, ejecuta el código C# y devuelve el resultado al modelo para que finalice su respuesta.

    Para habilitar este comportamiento en .NET:

    using Microsoft.SemanticKernel;
using Microsoft.SemanticKernel.Connectors.OpenAI;

var builder = Kernel.CreateBuilder();
builder.AddAzureOpenAIChatCompletion("model-id", "endpoint", "api-key");
builder.Plugins.AddFromType<SearchPlugin>();
builder.Plugins.AddFromType<CalculatorPlugin>();

var kernel = builder.Build();

// Configuración de la invocación automática de herramientas
OpenAIPromptExecutionSettings settings = new() 
{ 
    ToolCallBehavior = ToolCallBehavior.AutoInvokeKernelFunctions 
};

string prompt = "Basándote en el manual, ¿cuál es el costo total de 5 unidades del motor X-100 incluyendo el IVA del 21%?";

var result = await kernel.InvokeScalarAsync<string>(prompt, new(settings));
Console.WriteLine(result);

    4.10.5 Planners: Estrategias de Razonamiento

    Mientras que el AutoInvokeKernelFunctions es ideal para tareas directas, los Planners se utilizan cuando el problema requiere una serie de pasos complejos.

    1. FunctionCallingStepwisePlanner: Es el estándar actual. Crea un plan paso a paso (Iterativo). Ejecuta una acción, observa el resultado y decide el siguiente paso (bucle ReAct: Reasoning and Acting).
    2. Handlebars Planner: Genera un plan completo en formato Handlebars antes de ejecutar nada. Es útil para flujos de trabajo más deterministas.

    Ejemplo de flujo agéntico en RAG: - Usuario pregunta: "¿La garantía del producto cubre daños por agua según el PDF?" - Agente razona: Necesito usar SearchProductSpecs con el término "cobertura garantía agua". - Agente actúa: Llama a la función de C#. - Agente observa: El PDF dice "Excluye daños por inmersión". - Agente genera: Responde al usuario que no está cubierto, citando la sección específica del documento.

    flowchart TD
    Q(["💬 Consulta Compleja"]) --> Thought["🤔 Pensamiento\n(¿Qué información necesito?)"]
    Thought --> Action["🛠️ Acción\n(Ejecutar Plugin / Función C#)"]
    Action --> Obs["👁️ Observación\n(Resultado de la herramienta)"]
    Obs --> Check{"❓ ¿Tengo suficiente\ninformación?"}
    Check -- No --> Thought
    Check -- Sí --> Final["🤖 Generar Respuesta Final"]

    4.10.6 Ventajas del enfoque agéntico en .NET

    1. Reducción de Alucinaciones: Al dar al modelo herramientas para verificar datos (como una función que valide IDs de productos en una DB real), la fidelidad aumenta significativamente respecto al RAG básico.
    2. Extensibilidad: Puedes añadir nuevas capacidades al sistema RAG simplemente creando una nueva clase en C# y registrándola como Plugin, sin necesidad de reentrenar el modelo o cambiar la lógica del prompt principal.
    3. Contexto Dinámico: El agente solo trae al contexto la información que considera relevante después de un primer análisis, optimizando el uso de tokens.

    Este enfoque prepara el terreno para el Capítulo 5, donde veremos cómo monitorizar estas decisiones automáticas mediante Application Insights y cómo asegurar que las funciones invocadas respeten los permisos del usuario (RBAC).
