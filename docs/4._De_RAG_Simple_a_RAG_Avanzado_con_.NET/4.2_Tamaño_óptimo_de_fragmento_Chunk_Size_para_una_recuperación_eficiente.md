# 4.2 Tamaño óptimo de fragmento (*Chunk Size*) para una recuperación eficiente

## 4.2 Tamaño óptimo de fragmento (*Chunk Size*) para una recuperación eficiente

Una vez superada la fase de preprocesamiento y extracción de texto de los PDFs (visto en el capítulo 3.1), nos enfrentamos a una de las decisiones de diseño más críticas en la arquitectura RAG: determinar el **tamaño de fragmento** o *Chunk Size*. Esta decisión no es meramente estética; influye directamente en la precisión de la búsqueda vectorial y en la capacidad del LLM para generar respuestas coherentes.

### La dicotomía del Chunk Size: Precisión vs. Contexto

El objetivo de un sistema de recuperación es encontrar la información más relevante para una consulta. El tamaño de los fragmentos de texto que indexamos en nuestra base de datos vectorial (como Azure AI Search o Qdrant) genera un compromiso (*trade-off*) entre dos factores:

1.  **Fragmentos Pequeños (ej. 100-250 tokens):**
    *   **Ventaja:** Mayor granularidad. Es más probable que el fragmento sea muy específico respecto a un tema, lo que facilita que la búsqueda vectorial encuentre coincidencias exactas.
    *   **Desventaja:** Pérdida de contexto. Un fragmento demasiado corto puede carecer del sujeto de la oración o de la información circundante necesaria para que el LLM entienda el significado completo.

2.  **Fragmentos Grandes (ej. 800-1500 tokens):**
    *   **Ventaja:** Proporcionan un contexto rico al LLM. La información suele estar completa dentro de un solo fragmento.
    *   **Desventaja:** "Dilución" de la relevancia. Al contener múltiples temas, el *embedding* resultante representa un promedio de varios conceptos, lo que puede dificultar que el motor de búsqueda vectorial lo identifique como la mejor respuesta para una pregunta específica. Además, corremos el riesgo de exceder la ventana de contexto del modelo generativo si recuperamos varios fragmentos grandes.

### Factores para determinar el tamaño óptimo

No existe un "número mágico", pero en .NET podemos guiarnos por los siguientes criterios técnicos:

*   **Modelo de Embeddings:** Si usamos `text-embedding-3-small` de Azure OpenAI, el límite es de 8191 tokens, pero indexar fragmentos de ese tamaño sería ineficiente. Los modelos suelen rendir mejor con fragmentos de entre 256 y 512 tokens.
*   **Estructura del PDF:** Un manual técnico con tablas y listas requiere fragmentos más pequeños para no mezclar instrucciones. Un documento legal con cláusulas largas puede beneficiarse de fragmentos mayores.
*   **Tipo de consulta esperada:** Si las preguntas de los usuarios son muy puntuales ("¿Cuál es el torque del tornillo A?"), fragmentos pequeños son ideales. Si son analíticas ("Compara la visión de sostenibilidad de 2023 vs 2024"), se requieren fragmentos más grandes.

### Implementación técnica en C#

Para garantizar que el tamaño del fragmento sea preciso, debemos trabajar con **tokens** y no con caracteres, ya que los LLMs y los modelos de embeddings tienen límites basados en tokens. En .NET, la librería `Microsoft.ML.Tokenizers` es la herramienta estándar para este propósito.

A continuación, se muestra un ejemplo de cómo calcular el tamaño de los fragmentos de forma programática:

```csharp
using Microsoft.ML.Tokenizers;

public class ChunkOptimizer
{
    private readonly Tokenizer _tokenizer;

    public ChunkOptimizer()
    {
        // Usamos el tokenizer de GPT-4 / GPT-3.5 (cl100k_base)
        _tokenizer = Tokenizer.CreateTiktokenForModel("gpt-4");
    }

    public List<string> CreateOptimalChunks(string text, int chunkSizeTokens, int chunkOverlapTokens)
    {
        var tokens = _tokenizer.Encode(text).Tokens;
        var chunks = new List<string>();

        int i = 0;
        while (i < tokens.Count)
        {
            // Calculamos el final del fragmento
            int end = Math.Min(i + chunkSizeTokens, tokens.Count);
            
            // Extraemos los tokens y los decodificamos de nuevo a texto
            var chunkTokens = tokens.GetRange(i, end - i);
            chunks.Add(_tokenizer.Decode(chunkTokens));

            // Si llegamos al final, salimos
            if (end == tokens.Count) break;

            // Retrocedemos el índice según el overlap (solapamiento) para no perder contexto
            i += (chunkSizeTokens - chunkOverlapTokens);
        }

        return chunks;
    }
}
```

### El papel del *Overlap* (Solapamiento)

En el código anterior, introducimos `chunkOverlapTokens`. El solapamiento es crucial (generalmente entre el 10% y el 20% del tamaño del fragmento). Su función es evitar que información crítica quede dividida justo a la mitad entre dos fragmentos, permitiendo que el final de un fragmento y el inicio del siguiente compartan suficiente contexto para mantener la continuidad semántica.

### Estrategia de evaluación

Para determinar si el tamaño elegido es el correcto antes de pasar a la fase de "RAG Avanzado" (Capítulo 4.3), se recomienda realizar pruebas de recuperación:

1.  **Indexar el mismo conjunto de PDFs** en tres colecciones diferentes (ej. 256, 512 y 1024 tokens).
2.  **Ejecutar consultas de prueba** y medir el *Recall* (¿Está la respuesta correcta entre los fragmentos recuperados?).
3.  **Observar el ruido:** Si recuperas fragmentos de 1024 tokens y el LLM se confunde con información irrelevante, debes reducir el tamaño.
